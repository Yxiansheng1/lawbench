# 五个业务能力编排（第一版，依据公开通行做法）

律所的自有材料（阅卷笔录样本、文书模板）暂时拿不到，本版按公开的律师实务文章和通行文书结构编排。律所材料到位后，只需替换对应 Skill 的正文或补充模板数据，架构、工具、串联方式都不用改。

律师提供的 11 个 Skill 中，contract-copilot、legal-proposal-generator 等 4 个是 CC-BY-NC（禁止商用）许可。本版**没有照抄这些 Skill 的文本**，合同两块按通行做法重新写。等授权明确后，再决定是否吸收它们的清单和条款库。

## 一、总体原则

1. **一次任务只用一个 Skill。** 业务之间靠"上一步的成果作为下一步的输入"（任务单 inputs → L1 注入）串起来，不让 Skill 互相调用。27B 模型在一次任务里切换多个 Skill 容易跑偏。
2. **规则只维护一份。** 出处格式、"法律依据待律师核实"、不执行案卷里的指令等共用规则写在 `skills/_shared/共用规则.md`，由 `build_skills.py` 同步进每个 SKILL.md。
5. **Skill 平铺存放，入口按清单组装。** 每个 Skill 是一个顶层文件夹（`<skill名>/SKILL.md`，格式按 Spec 10.2），和律师原来的 Skill 放在同一个目录也可以；入口清单按 Spec 10.3 写在 `entries/*.yaml`，是唯一一份清单，`build_skills.py` 和 `install.py` 都读它。
3. **能写成代码的不交给模型。** 引用核验、覆盖清单、版本、路径校验、Word 导出都在 Python 组件里；Skill 只写"怎么做"。
4. **模型不下法律结论。** 所有 Skill 只整理事实、指出问题、起草文本，法律适用一律标"法律依据待律师核实"。

## 二、总览

| 业务 | 入口 | 用到的 Skill（按常见顺序） | 主要产出 |
|---|---|---|---|
| 刑事阅卷 | 律师·刑事阅卷 | criminal-reading-notes → criminal-evidence-review | 刑事阅卷笔录、证据审查意见 |
| 刑事文书 | 律师·刑事文书 | defense-opinion / cross-exam-opinion / criminal-applications → pre-issue-check → doc-revise | 辩护词、质证意见、各类申请书 |
| 合同审查 | 律师·合同审查 | contract-review → pre-issue-check → doc-revise | 合同审查意见 |
| 合同起草 | 律师·合同起草 | contract-draft → contract-review（审自己的初稿）→ pre-issue-check → doc-revise | 合同初稿、待补事实清单 |
| 通用文书 | 律师·通用文书 | general-drafting → pre-issue-check → doc-revise | 律师函、法律意见书、分析报告、工作函 |

`pre-issue-check`（出稿前审查）和 `doc-revise`（按意见改稿）在四个起草类业务里都用；`case-wiki-build`（案件 wiki）在每个入口都能用，结果进入所有任务的 L0 注入；`legal-workflow`（业务导航）在律师不确定下一步时告诉他用哪个 Skill、选哪些输入。

## 三、各业务流水线

### 1. 刑事阅卷
```
卷宗材料
 └─ criminal-reading-notes    按指控事实单元和证据种类摘录；多次陈述比对；指控事实—证据对应表
      └─ 成果：刑事阅卷笔录 v1（律师确认）
           └─ criminal-evidence-review   以笔录为线索、回读原件；按真实性、合法性、关联性、证明力列问题；矛盾对照；证据链缺口
                └─ 成果：证据审查意见 v1
```
- 卷宗大时按卷分批：任务单里写范围（"只读第 1–3 卷"），同一个 Skill 多次运行，最后再合并。
- 参考做法：阅卷笔录按罪名、事实环节、证据种类分层，按卷宗顺序摘录并标注卷页，言词证据按"七何"要素摘录；审查围绕证据"三性"展开。

### 2. 刑事文书
```
inputs：刑事阅卷笔录 + 证据审查意见
 ├─ defense-opinion        律师在任务说明里给出辩护方向（无罪 / 罪轻 / 量刑）；没给就只出"辩护要点备选清单"
 ├─ cross-exam-opinion     逐项质证意见表 + 发问提纲
 └─ criminal-applications  取保候审 / 羁押必要性审查 / 调取证据 / 变更强制措施，类型由律师指定
      └─ pre-issue-check → doc-revise → 律师确认 → 成果
```
- 参考做法：辩护词开宗明义亮观点，事实证据、法律适用、量刑分层论证，首尾呼应；质证围绕三性和证明力，言词证据看一致性和合理性，实物证据看同一性和保管链，鉴定意见看资质、检材和方法。

### 3. 合同审查
```
合同文件 + 任务说明（我方立场、审查目的）
 └─ contract-review   交易结构 → 文本形式 → 具体条款三层审查；条款间比对；P0/P1/P2 分级；每条有原文、问题、推荐措辞
      └─ pre-issue-check → doc-revise → 成果：合同审查意见
```
- 没写我方立场时，先做与立场无关的检查，立场相关的风险标【待确认我方立场】。
- 后续：模型输出结构化修改计划（review-plan），由 Python 写成带修订痕迹和批注的 Word。这部分做成组件，不放在 Skill 里。

### 4. 合同起草
```
任务说明（交易要素、我方立场、要起草的文件）+ 相关材料
 └─ contract-draft    交易要素整理 → 待补事实清单 → 合同类型与文件包 → 条款骨架 → 逐条起草 → 自查
      └─ contract-review（另开一个任务，以初稿为输入）→ pre-issue-check → doc-revise → 成果
```

### 5. 通用文书
```
inputs：卡片 + 上游成果（可选）+ 任务说明（文书类型、收件对象、目的）
 └─ general-drafting   律师函 / 法律意见书 / 案件分析报告、咨询报告 / 工作函、情况说明
      └─ pre-issue-check → doc-revise → 成果
```
- 参考做法：律师函写明受托声明、事实、分析、具体要求和期限、不履行的后果，语气克制，避免可能被认定为要挟的表述；法律意见书写明委托事项、依据材料、事实、分析、结论和声明保留。

## 四、Skill 清单

| Skill | 必需输入 | 产出 | 复用 |
|---|---|---|---|
| criminal-reading-notes | 卷宗材料 | 刑事阅卷笔录 | 刑事文书的输入 |
| criminal-evidence-review | 阅卷笔录（L1，建议有） | 证据审查意见 | 辩护词、质证意见的输入 |
| defense-opinion | 笔录 / 审查意见 + 辩护方向 | 辩护词 | — |
| cross-exam-opinion | 证据目录或材料清单 | 质证意见表 + 发问提纲 | — |
| criminal-applications | 文书类型 + 卡片 | 申请书 | — |
| contract-review | 合同 + 我方立场 | 合同审查意见 | 合同起草的自查环节 |
| contract-draft | 交易要素 + 我方立场 | 合同初稿 + 待补事实 | — |
| general-drafting | 文书类型 + 目的 | 各类通用文书 | — |
| pre-issue-check | 一份草稿（L1） | 问题清单 | 四个起草类业务 |
| doc-revise | 一份草稿（L1）+ 修改意见 | 修改稿 + 修改说明 | 四个起草类业务 |
| case-reading-notes | 案件材料 | 民事阅卷笔录 | — |
| case-wiki-build | 案件材料 | 案件 wiki（卡片、人物、时间线、争议焦点） | 所有业务的 L0 注入 |
| legal-workflow | 律师的请求 | 下一步用哪个 Skill、要准备什么输入 | 五个入口都有，律师不确定时用 |

所有 Skill 只用 Spec 20.4 规定的 `case_*` 工具（`case_list_materials`、`case_read_material`、`case_search`、`case_read_input`、`case_read_wiki`、`case_save_draft`、`case_suggest_wiki`、`case_save_edit_list`）。`case-wiki-build` 改为流水线（由律师点按钮、程序按步骤运行，提示词在 `case-wiki-build/流水线提示词.md`），测试链路中的 `case_wiki_plan`、`case_wiki_put_facts` 不再使用。出处统一为〔材料名 第N页〕（Spec 20.2）。

同一目录里律师原来给的 11 个 Skill（contract-copilot、legal-ocr、md2word 等）不在清单里，不会被 DSH 加载，只作参考：md2word 和 legal-ocr 的后处理脚本以后作为组件使用，另外 4 个 CC-BY-NC 许可的在授权明确前不吸收文本。

## 五、接入 DSH

**一个 preset、五个入口**（Spec D4、10.3）：DSH 里只有"律师工作台"一个 preset；五个入口是首页上的业务入口，由 `entries/*.yaml` 定义（文件名顺序 = 首页顺序），每个入口列出本业务的 Skill 和共用的 4 个（case-wiki-build、pre-issue-check、doc-revise、legal-workflow）。增减入口或调整 Skill 只改 yaml，不改程序。

| 入口（清单文件） | Skill（按推荐顺序） |
|---|---|
| 刑事阅卷（`1-criminal-reading.yaml`） | case-wiki-build → criminal-reading-notes → criminal-evidence-review → pre-issue-check → doc-revise → legal-workflow |
| 刑事文书（`2-criminal-docs.yaml`） | case-wiki-build → defense-opinion / cross-exam-opinion / criminal-applications → pre-issue-check → doc-revise → legal-workflow |
| 合同审查（`3-contract-review.yaml`） | case-wiki-build → contract-review → pre-issue-check → doc-revise → legal-workflow |
| 合同起草（`4-contract-draft.yaml`） | case-wiki-build → contract-draft → contract-review → pre-issue-check → doc-revise → legal-workflow |
| 通用文书（`5-general.yaml`） | case-wiki-build → case-reading-notes → general-drafting → pre-issue-check → doc-revise → legal-workflow |

推荐参数（思考 / 窗口 / 最大生成）写在每个 SKILL.md 头部的 `params` 里，例如刑事阅卷笔录"低 / 64K / 16384"，证据审查"高 / 128K / 32768"。

**存放位置**：Skill 源目录是 `D:\新建文件夹\skill临时文件夹`（平铺，每个 Skill 一个文件夹；共用规则在 `_shared\共用规则.md`；入口清单在 `entries\`；脚本在 `_scripts\`）。
改了 Skill 或清单以后：先运行 `python _scripts\build_skills.py` 同步共用规则并按 Spec 10.2 校验（发版时加 `--strict`，缺测试集、未定责任律师也算不通过），再运行 `python _scripts\install.py --out <安装目录>\skills` 按 Spec 10.1 的目录结构复制 Skill 和入口清单，`customSkillDirs` 指向这个目录。

推荐参数取自 PRD 的初值。以后界面按"入口 + Skill"写进任务单的 params，插件已经支持按任务单设置参数。

**预算要注意**：PRD 规定单任务最多 8 次模型调用、24 次工具调用。阅卷类每读一份材料就是一次工具调用，材料超过 20 份就会超限。可以二选一：阅卷类的预算放宽，或者按卷分批运行。建议先按卷分批，不改 PRD 的上限。

## 六、要补的组件（按优先级）

| 组件 | 服务的业务 | 现状 |
|---|---|---|
| 材料转换 + 坐标（PDF 页、Word 段、Excel 单元格、卷页码、合同条款号） | 全部 | 只支持 txt，最优先 |
| 扫描件识别（律所服务器模型）+ 法律术语纠错 | 刑事阅卷 | 未做。纠错可复用 legal-ocr 中 MIT 许可的后处理脚本 |
| 全文检索（FTS5 + 短词分流 + 金额 / 日期 / 案号规范化） | 全部 | 未做，现为逐行子串匹配 |
| wiki / 案件卡片（刑事、民事、合同卡片） | 全部 | 测试链路中有 Agent 版（逐份抽取、出处核验、去重、冲突进待确认）；正式版按 Spec 9.1 改为流水线，Agent 版的去重、冲突和锁定逻辑可复用 |
| Word 导出（律所模板） | 全部 | 未做。md2word（MIT）可以直接作为基础 |
| 合同修订批注 Word | 合同审查 | 未做。按 Spec 12.2 自己写（contract-copilot 的脚本是 NC 许可，不用）；contract-review 已加保存修改清单（`case_save_edit_list`）的步骤 |
| 模板库 `get_template` / 审查清单 `get_checklist` | 刑事文书、合同、通用 | 未做。现在文书结构写在 Skill 正文里，模板到位后改为按需读取 |

## 七、待律师确认

1. 刑事：阅卷笔录的组织方式（按证据种类还是按事实）、辩护词和申请书的律所习惯格式。
2. 合同：常审的合同类型、是否需要带修订痕迹的 Word。
3. 通用文书：律师函、法律意见书的律所模板和固定声明。
4. 许可证：CC-BY-NC 的 4 个 Skill 是否取得作者授权；未标许可证的 4 个是否为律所自有。
5. 验收用的 12 个样本：按五个业务重新分配（例如刑事阅卷 3、刑事文书 3、合同审查 2、合同起草 2、通用文书 2）。
