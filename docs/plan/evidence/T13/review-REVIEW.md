## 一、Findings（按严重度）

### P2-1 输入区切回"自由对话"时不写任务单，上一张胶囊任务单仍在待执行，下一条消息会按旧 Skill 跑（范围内阻断）
- **问题**：律师先选了胶囊 A（界面已写入一张 entry=A 的任务单），又改回"自由对话"。这时界面直接 `setStatus(null); return`，不写任何东西。结果 A 那张单子仍是 pending，律师发出的下一条消息会按 A 的 Skill 执行。
- **违反的不变量**：输入区上方显示的选择 = 下一条消息实际使用的任务单。契约 `task_create.schema.json` 里 entry 的描述写明"自由对话为 null"，也就是说契约本来就预期界面在自由对话时写一张单子。
- **影响**：律师以为在自由对话，实际跑的是 Skill，还可能按那个 Skill 读更多材料、发往 6000D。界面上看不出来。
- **证据**：
  - `dsh-ext\ui\dock.tsx:47-56`（第 49 行提前 return）。
  - 线 B 的实现 `origin/line-B:service/lawbench/case/task.py:180-192`：`_pending_for` 取同一会话中 created_at 最新的一张 pending 单子，没有作废旧单子的逻辑。
- **最小修复**：本会话写过单子之后，切回自由对话也写一张 `{entry:null, skill:null, inputs:[], params}`，并补一条单测。

### P2-2 假数据测试在本机默认 git 设置下重新检出后 31 项红（范围内阻断）
- **问题**：`tests\fixtures.spec.ts:32` 断言假数据文件里没有 `\r`。可是本机系统级 gitconfig（`D:/git/Git/etc/gitconfig`）设了 `core.autocrlf=true`，仓库也没有 `.gitattributes`，任何一次新检出都会把 `ui\fixtures\*.json` 写成 CRLF。
- **影响**：作者工作树里的文件是新写的、行尾是 LF，所以作者那里是绿的。合并到 main 以后，主编排在 `D:\lawbench`、T14 联调检出的都会是 CRLF，`node scripts/test.mjs` 退出码为 1，合流门过不了。
- **证据**：
  - 我在复核克隆的副本里跑 `node scripts/test.mjs`：13 个文件里 1 个失败，共 31 failed / 111 passed / 5 skipped；失败信息是 `expected '{\r\n "ok": true…' not to contain '\r'`。
  - 把 31 个假数据文件改回 LF（只动实验副本）后重跑：142 passed / 5 skipped，与作者的 `ts-test.txt` 一致。
- **最小修复**：二选一。加一行 `.gitattributes`：`dsh-ext/ui/fixtures/*.json text eol=lf`；或者测试读文件后先把 `\r\n` 规整成 `\n` 再判断。

## 五、重点各条的结论

**界面插件和 Host 新代码能不能读写案件文件**
- 界面：没有途径。唯一读取的本地字节是剪贴板里的 File，读完交给 Host。
- Host：粘贴截图的临时目录固定为 `<appData>\临时\粘贴`，appData 来自 cordis 配置里的 LOCALAPPDATA；图片只收 PNG / JPEG 文件头；不论导入成功、失败还是抛异常都会在 finally 里删临时文件（M5 变异两项变红）；启动清理只动这个目录。不足：文件名随机性不足、大小检查偏晚（P3-4）；和启动清理同时发生的粘贴属于臆测风险。
