## Findings

### P2｜同根因未关闭（P2-A → P2-1 → 本轮）：状态行显示"就绪"时，参数框和服务存的仍会不同

- **问题一句话**：本轮加的是"已保存、但显示的键不是服务那份就重写"。可这次重写期间，选择仍记为"已保存"，状态行一直是绿字；重写失败之后 `serverKey` 为 null，再有参数变化就既不重写、也不报错。
- **根因**：和前两轮相同。"已保存"这个判断（管状态行，也管写不写）没有把"显示的键 ≠ 服务那份"算成"没保存"。

**路径 ①：Skill 列表回来后的约 0.5 秒空窗（确定能复现）**

- 每档都采到 20 个样本（每 25 毫秒采一次，也就是整整 500 毫秒防抖，再加写入耗时）。
- K1b：列表回来后 50 毫秒发送，状态行是就绪，参数框 64K，服务 128K。这一轮实际按 128K 跑。
- 列表慢 0.3 秒（比第一次写入早回来）时是 0 个样本。

**路径 ②：永久不一致（K3e，两种挂载模式都复现）**
1. 默认参数 128K 写成；
2. Skill 列表 1.5 秒回来，触发重写；

**最小修复（方向）**

### P3｜本次引入（`a8ffb5a` 的 P3-1 串行化）：`notice()` 自己抛错时 `load()` 不再执行

- **问题**：挂上时改成了 `notice().then(load)`，但没有处理 `notice()` 失败的情况。
- **影响**：`turnNotice` 返回的形状不对（例如 `{ok:true, value:null}`）时，`r.value.code` 会抛错，`load` 就永远不跑。状态行卡在"正在读取当前选择…"，首页或成果区的意向不会取走，还有 1 个未处理的 Promise 拒绝（N2）。
- **现实里多不多**：Host 的 `turnNotice` 目前总是返回 `{code}`；Host 方法本身 reject 时由 `call()` 兜住，`load` 照常跑（N1 已验证）。所以只在 Host 返回不合形状时才会出现，概率低。一轮结束那条路径（`387c635` 起）本来就是这样。
- **最小修复**：`notice().then(load, load)`，或在 `notice` 里 try/catch。
- **归类**：本次引入的回归（低概率）。

### P3｜测试缺口：一轮结束时"先取提示再读"的顺序没有用例守着
