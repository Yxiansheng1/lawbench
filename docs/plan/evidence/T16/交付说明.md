## 3. 做法

### 3.1 提示词合并（步骤 1）
以 wiki 测试实测版为底：通用规则 8 条、材料摘要、四篇的写法照抄实测版；去掉"刑事案件"限定，加民事、合同的说法（原告、被告、合同条款）；出处统一〔材料名 位置〕，支持页、段、行；材料摘要里出处只写位置（〔第N页〕），由程序补材料名（实测稳定）。"案件卡片"取仓库草稿版（实测版没有这一步），加了条数和字数上限。"修改"段按 Spec 9.1 改成只交问题句、按序号回改好的句子。争议焦点的检查清单加了"不同人对同一件事的说法不一致"（通用写法）。

**合并时对实测版的删改（返修 P3-5 补写）**：
- 删："修改"一段的全文重写写法（改为只交问题句，Spec 9.1）；"刑事案件"限定（改为通用说法）。
- 曾删、返修补回：材料摘要里"银行流水、通话详单只列 ① 户名账号期间、② 对方是人名的转账、③ 金额 ≥10,000、④ 含 ■ 或 [看不清] 的行、⑤ 取现，其余合成一条；通话详单只写机主、号码、期间、总条数和出现最多的号码"两条。第一版以为表格类材料都由程序筛选，就删了；复核指出表格行占比不到 60% 的材料仍交模型，这两条照实测版原文保留作兜底，后面加一句"表格行占多数的材料由程序筛选，不会交给你"。
- 加：民事、合同的说法；出处支持段、行；"案件卡片"一段（仓库草稿版 + 条数字数上限）；争议焦点清单一条。

### 3.2 框架（步骤 2）
- **6000D**（`llm.py`）：经 `Net`（白名单、所内所外自动切换、不跟随重定向）发 `POST /chat/completions`，`model` 固定 `qwen38-27b`，`stream: true`，思考"关闭"发 `enable_thinking: false`，低/中/高发 `reasoning_effort` low/medium/**xhigh**；`Authorization` 用律师 Key（凭据管理器，不落盘不进日志），`X-Session-Id` 为任务编号。错误按 Spec 8.3 映射（连不上重试 1 次 → SERVER_UNREACHABLE；401/403 → KEY_INVALID；503 → SERVER_BUSY；400 含 context length → CONTEXT_TOO_LONG；超 1200 秒 → TIMEOUT；返修后读超时 → TIMEOUT、连接中途断开等其余网络错误 → SERVER_UNREACHABLE，不再记异常类名）。**取消（返修 P2-1）**：每次请求单独一个 client（`Net.own_client()`，钩子与超时同 `Net.client`），在后台线程里读；本线程每 0.1 秒查取消标志和 1200 秒计时，到了就关掉这个 client 断开连接，不等响应头、不等下一行。395 同一个取消标志，每段前查、在途请求同样可断。**窗口（返修 P3-6，最小版）**：发送前按 `llm\tokens.py` 计"系统提示 + 本步输入 + max_tokens"，超过律师选的窗口不发、该步报 CONTEXT_TOO_LONG（整次 failed）；"切小再发"是独立后续。**并发（返修 P3-2）**：进程内一个 2 名额的信号量，多个案件同时跑也最多 2 路；等名额的时间和排队一样不计入 45 分钟。
- **步骤**（`runner.py`）：调用 → 清理 → 逐行用 T10 的 `checks.check_text` 核（kind 按 SKILL.md，wiki 是 excerpt），A、B、C、D、E、G 里 must_fix 的算有问题 → 只把问题句编号、附问题说明和相关原文（所引位置与"实际在"的位置）交"修改"步骤 → 按序号换回 → 最多 2 轮，改完没变化就停。
- **程序兜底**（`Runner.settle`，大卷宗实测后加的，见第 5 节第 6 条）：两轮修改后仍有 must_fix：A 类不动出处、在出处前插注"原文…为'陈美■'，识别不清，需核对原件"；B 类把出处改到"实际在"的那一处；C、E 类只把有问题的那组出处改标〔未找到依据〕；还不过的整句出处改标〔未找到依据〕；G 类程序改不了，留着如实报告。改过的句子记进运行记录的修改记录（"程序兜底"）。
- **预算**（Spec 9.1）：调用次数上限 = 段数 × 3 + 篇数 × 3 + 10（篇数 = 四篇 + 卡片 = 5）；45 分钟，排队时间（`X-Queue-Wait-Ms`）不算。到上限保存已完成的部分，状态 `budget_stopped`。
- **并行度 2**（Spec 8.5）；**进度**："第 k 步 / 共 n 步，当前：材料名"；`queue_wait_ms` 取最近一次。
- **任务记录**：P- 任务（`task.json` kind pipeline、step、budget；`result.json` 状态、用量、草稿、全文核对、结构化出处）；`运行记录.json`（任务目录里）。**更正（复核 P3-1）**：第一版说它"只有元数据"，与实际不符——"对象"写的是材料名（"起诉意见书#1"），修改记录里有问题说明原文和兜底改动的原句片段（含日期、人名）。返修后：对象写材料编号（摘要 `M0001#1`；四篇写节名；卡片写"案件卡片"），修改记录只写"第 N 行 + 问题类别"，兜底只写"第 N 行 + 做法"（如"B 挪到实际位置"）；395 一项只有计数和提示。字段：状态、错误码、调用次数、耗时、单次最大输入字数与 token、截断次数、预算、395、修改记录、每次调用（步骤、对象、耗时、输入字数、输入/输出 token、结束原因、排队毫秒）。它不在 Spec 20.8 的落点表里，由主编排补登记。
- **日志**：服务日志只记 `pipeline/begin|end|run`、案件编号、耗时、错误码；不记提示词、模型输出、材料名（有测试）。

### 3.3 案件 wiki（步骤 3）
- **文件**（与 `case_read_wiki` 一致）：`工作区\wiki\材料\<材料编号>.md`、`案件\<节名>.md`、`case.json`、`index.md`、`log.md`。跑完直接写进 `工作区\wiki\`（默认做法 1），四篇和卡片另存一份到任务 `草稿\`。
- **摘要**：页、段、行材料按单元切段（约 8000 字）；表格类（以 | 开头的行 ≥ 60%，Excel 一律算）由程序按筛选条件列行，其余计数，摘要页第二行写"> 筛选条件：…；已列出 X 行 / 共 Y 行"，材料清单注明"摘要为筛选结果，非全量"；筛选条件读 Skill 目录的 `表格筛选.json`，没有就用默认四条（本次没建这个文件，用默认）；程序统计行的出处合并成页码范围。
- **材料清单、目录、日志**：程序写；失败、待识别的材料列为未读，原因照抄导入记录；原件已删除的注明"保留材料文本"。
- **卡片**：一次调用；JSON 解析失败或被截断（`finish_reason=length`）时提示精简后重试一次，还不行不写空卡片、不覆盖原卡片、整次运行记 `failed`（OUTPUT_TRUNCATED）。每处出处和条目文字一起过 T10 核对，有 A–E 问题的出处丢掉、条目改 `unconfirmed`；编号 F0001 起按 parties → issues → key_facts 顺序由程序分配，旧卡片里律师确认的条目排在各类前面保留，本方立场保留；`materials_at_generation` 记材料编号与 sha256。
- **律师修改块**：写任何 wiki 文件（返修后含 `index.md`）前先取出旧文件里的块，按块前一行原样放回；中间只隔空白的连续几块算一组整组放回，同一位置的几组按原先后（返修 P3-4）；原位置不在了放文末并加 `> **Status: 待律师核对**`。
- **更新**（wiki_update）：与 `case.json` 的 `materials_at_generation` 比 sha256，只重跑新增或变化材料（以及没有摘要页、或摘要页只有部分的材料）；其余沿用旧摘要页；四篇、卡片、清单、目录、日志重写。
- **中途停下（返修 P2-4，主编排定）**：取消、到预算、某段出错时，已有完整摘要页的不覆盖，半份存任务 `草稿\材料摘要 <编号> 部分（k 段，共 n 段）-v1.md`，清单那行仍"是"、备注"本次运行中止，保留上次的摘要页"；没有旧页的才写半份，页首第二行 `> 部分摘要：部分（k/n 段），运行中止，没有读完`，清单那行写"部分（k/n 段）"；一段都没写的写"**否**｜运行中止，未生成"。停下时材料清单照此重写。
- **开跑前建目录（返修 P2-2）**：`材料\`、`案件\`、任务 `草稿\` 先建好，避开两路并行第一次建目录时 `gate._real_top` 的 `\\?\` 误判（闸门本身归 T3 后续）。
- **旧卡片坏了（返修 P3-7）**：`case.json` 存在但不合契约（不是 JSON 或校验不过）时不覆盖、整次 failed，错误码 INVALID_ARGUMENT（见第 7 节待定）。
- **日志 log.md**：读改写拿 `tools\drafts._WIKI_LOCK`（与采纳修改建议同一把锁）。
- **全文核对**：四篇与全部摘要页逐份核对，合并进 `result.json` 的 `citation_check` 与 `citations`。
