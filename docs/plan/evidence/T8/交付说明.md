## 5. 契约与文档

没有改契约和文档。以下几处按下面的取法实现，请 ORCH 定：

1. **Excel 的 `start` / `end` 怎么数。**
   - formats.md 第 2 节原文："Excel 为工作表内的行号，跨工作表时从下一个工作表的第 1 行重新计数"。
   - 按这个写法，只凭一个 `start` 分不清是哪张工作表的第几行，所以翻页没法跨工作表。
   - 现在的取法：Excel 的位置号是整份材料里表格行的顺序号，从 1 起，跨工作表连续；返回的 `text` 里保留 `【表:…】` 标记和工作表内的真实行号，出处照常写 `工作表!B12`。`reads.json` 和覆盖清单也按这个顺序号记。
   - 如果要严格照 formats 的写法，需要在参数里加工作表名，那是改契约。
2. **需识别的材料能不能读。**
   - 整份都是"本页需识别"占位的（扫描件、图片）报 `MATERIAL_NOT_READY`；有一部分文字页的照常读，占位页原样返回。
   - Spec 20.1 原文："材料未解析完、待识别或失败"。
3. **`case_search` 是临时实现。** 逐单元子串匹配，没有 FTS5 和日期、金额的查询扩展，`match` 恒为 `exact`。T9 替换，接口不变。
4. **出处核对由 T10 接入。** 本卡 `case_save_draft` 返回空的 `citation_check`：`passed: true`、问题数 0（工单原文）。
5. **L1 只放任务单选用的输入。** 契约 `task.json` 里没有"wiki 分节"字段，Spec 9.2 提到的"wiki 分节"没法按任务单选用。现在 AI 用 `case_read_wiki` 自取。
6. **L0 标"wiki 生成后新增或修改"** 是按 `case.json` 的 `materials_at_generation` 对比当前 sha256 得出的。
7. **修改清单的段号从 docx 原件重新数。** 数法与材料解析相同：正文非空段落、表格算一段、页眉页脚是最后一段，这样"段号与材料文本一致"。docx 原件在解析之后被改过的，段号可能对不上；这种情况下原件和材料都会显示为"变化"，律师重扫即可。

## 8. 近似 token 计数（注记 2332 第 2 节）

**估算方法**（`llm\tokens.py` 的 `count`）：刻意偏大，因为它用来控制"输入不超过窗口的 40%"，少算会让请求超出模型窗口。

| 字符 | 按多少 token 算 |
|---|---|
| 中日韩文字、全角符号 | 每字 1（Qwen 系分词器对常见汉字通常一字不到 1 token） |
| 数字 | 每位 1（Qwen 系把数字逐位切开） |
| 英文字母 | 连续一串按每 3 个字母 1 向上取整（常见实测约 4 个字母 1 token） |
| 其他 ASCII 符号 | 每个 1 |
| 空白 | 连续的算 1 |
| 其余非 ASCII 字符 | 每字 2 |

**与真实长度的偏差：未核实**，因为没有 tokenizer。按上面的依据，预计中文材料会多算约一至三成，含大量数字的流水类材料接近真实。`tokenizer.json` 取到后，`tokens.is_exact()` 为真，改用真计数；那时可以用样本核一次偏差，写进 T18 的预算实测。

测试：`test_tokens.py`，覆盖汉字、数字、日期、英文、出处文本 5 种写法的下限，以及空文本和 L1 上限。
