## 一、问题清单

**P2-A 页卡在"发送中"，任务永远停在 running，重开案件也救不回**
- **问题**：`_worker` 兜底时，`_set_page(..., timeout=1.0)` 失败只记日志，页留在 `sending`。但任务仍在 `self._jobs` 里：
  - `_next` 只挑 `pending` 的页，这一页不会再被挑到；
  - `_resume_case` 跳过内存里已有的任务（`if r[0] not in self._jobs`）。
  
  所以交付说明 P2-1 那行"重开案件或重启时回到待发送"里，"重开案件"这一半不成立。
- **影响**：任务一直 `running`，`pause_reason` 为空，界面像在识别，实际不动，只有重启服务才恢复。这正是冻结清单 P2-1 要消除的"静默停摆"，只是从整个队列缩小到了单个任务。
- **证据**（`rv-C16-T12-lab\test_lab_c16.py`，输出在 `lab-tests.txt`）：
  - `test_x1_lock_while_page_in_flight`：395 正在处理第 1 页时，另一个连接用 `BEGIN IMMEDIATE` 占住 case.db 20 秒。日志依次出现 `ocr page fail OperationalError`（写"已完成"10 秒超时）、`page_reset fail`。
    - 放开锁 15 秒后：`running`，页 `{1: ('sending', 0)}`。
    - 再调 `/api/case/open` 等 10 秒：仍是 `running / sending`。
    - 线程都活着。
  - `test_x3_vanish_while_in_flight`：页在途时文件夹被移走，4 秒后插回并 `case_open`。结果 `done=1/2`，任务停在 `running`。原因是兜底里设了 `skip_until` 5 秒退避，这段时间 `_next` 不会把任务移出内存；`case_open` 又跳过内存里的任务，在途那页就成了孤页。
  - 盘真的满时同理：结果文件写不进去，case.db 的计次 UPDATE 也可能写不进去，页也会卡在 sending。这一条是推断，没有实测。
- **最小修复**：在 `_next` 里（已持 `_cv`，`job.claimed` 是唯一可信的"在途"），把该任务里 `status='sending'` 且页号不在 `job.claimed` 的页先改回 `pending`。这样不用重开案件也能自愈。另一种办法是 `_resume_case` 对内存里的任务也重置未被领走的 sending 页。
  - 同一类：`_maybe_finish` / `_finalize` 的库超时如果抛错，会出现所有页都完成但任务一直不收尾。可以在 `_next` 发现"没有待发、也没有在途页、状态仍未结束"时调一次 `_finalize`。
  - 补 x1、x3 两条用例；交付说明里"重开案件"那句要改。
- **归类**：范围内阻断（冻结清单 P2-1 没有完整关闭）。

**P3-A 保存设置会被锁住的 case.db 卡 10 秒 × 任务数**
- **问题**：`settings.on_change` 在请求线程里同步跑 `resume_key_invalid → _resume_where`。它对内存里的每个任务都开一次 case.db，库超时是 10 秒；没有任何任务因 Key 暂停时也照样执行。
- **证据**：`test_x2`，两个任务所在的案件 case.db 被占时，`PUT /api/settings` 用了 **21.47 秒**。
- **最小修复**：
  - `resume_key_invalid` 只在 `_bad_key is not None` 时才动库；
  - 或者只设一个标志，交给探测线程去做；
  - 或者 `_resume_where` 用短超时（例如 1 秒）。
- **归类**：本次引入（134b220）。

**P3-B 防冒充标记：线 C 口径比契约宽，合并器自己的拆页正则也宽（主编排要判的那一条）**
- **① 更宽有没有害**：
  - 对检索和逐字引用核对基本无害。T9 的 normalize 先用 NFKC 把 U+3000 变成普通空格，再去掉汉字之间的空白；T10 evidence 两边都去掉全部空白。所以 T10 的 ≥6 字匹配不受影响。
  - 害处在两处：
    - 识别文本里正常以【开头的行（聊天截图里的"【2025-03-10 21:14】周立新：…"）被改动；同一份材料里，文字层的页不改、识别的页改，前后不一致；
    - 违反契约 `formats.md` 第 2 节："恰好与标记完全相同的整行"才转义，"以【开头的其他行一律是正文"。
  - 探针 `escape_probe.txt`：同一行，线 C 输出 `'\u3000【2025-03-10 21:14】…'`，main 输出原样。
- **更要紧的是合并器自己的拆页正则**：`merge.py` 的 `_PAGE_MARK = ^【第(\d+)页】\n?` 只看行首。T5 文字层里的一行"【第9页】伪造"（main 口径不转义）被合并器拆开后，重写成独立的 `【第9页】` 标记行。
  - 探针结果：`merge stats {'pages': 4}`；用 main 读侧拆页得到 `['第1页','第9页','第2页','第3页']`，原来那行文字没了。
  - 线 C 用更宽的转义，其实是在替这条宽正则兜底，而它只兜得住识别文本，兜不住文字层。
  - 归类：此前既有（cea2d9d），合进 main 后才显出来。
- **② 维护代价**：两个模块里各有一个同名 `escape_marks`，语义不同；读侧 `texts._MARKS` 和合并侧 `_PAGE_MARK` 两套正则也不一致，以后改一边很容易漏另一边。
- **③ 结论，同意主编排倾向**：rebase 到 main 后：
  - `merge.py` 直接 `from ..case.materials import escape_marks`，删掉本地那份；
  - `_PAGE_MARK` 改成整行口径：`^【第([0-9]+)页】(?:\n|$)`，或直接复用 `texts._MARKS["page"]`；
  - 用例 `test_ocr_line_like_page_mark_escaped` 里"`\u3000【第9页】伪造`"那条断言改成"原样保留、不被拆页"；
  - 补一条"文字层行首带标记的行，合并后页数不变"的用例。
- 这两处改动都很小，可以和 P2-A 一起做。

**P3-C 两条修法没有用例能稳定抓住**
- **M3（把 `_next` 逐任务兜底整块撤回）**：4 次里 3 次绿、1 次红。原因是 job_id 尾部是随机串，同一秒提交的甲乙两个任务先后不定；乙排在前面时，甲打不开也挡不住乙。
  - 修：用例里让甲先提交、隔 1 秒再提交乙，或者直接断言甲排在前面。
- **M2（撤掉 `_process` 开头的文件夹检查）**：作者用例全绿。作者的用例都是"启动前就移走"，被 `_next` 先拦下了；页在途时被拔这条路径没有作者用例覆盖。
  - 修：补 x3 那样的用例（修完 P2-A 后应该是绿的）。
- **归类**：范围内，非阻断。

**NOTE**
1. **case_open 与收尾的竞争（推断，未复现）**：`_finalize` 先把任务移出内存，再合并（可能几秒），最后才标完成。这中间如果 `case_open` 触发 `_resume_case`，会把这个任务重新放回内存。它随即被标为 done，但留在内存里成为空转条目，每轮被读一次库，直到重启。无害但会泄漏。
2. **"取消 5 秒内断开"的边界**：取消时如果正卡在 pdfium 锁上等渲染（T5 正在解析长 PDF），`_senders` 清空会超过 5 秒。但这时没有在途的 HTTP 请求，"在途请求 5 秒内断开"仍然成立。
3. **Key 轮询**：只在有 key_invalid 暂停时才每 30 秒读一次凭据管理器，本机读，代价可以忽略。
   - 读失败时 `keyring_key` 每 30 秒记一行 `keyring_read fail`（只有类名）。
   - 被暂停的任务取消后，`_bad_key` 不会清空，会一直轮询到 Key 变了为止，代价可忽略。
   - 指纹是不加盐的 sha256，只在内存里比，不进日志。
4. **M6b 绿是预期内**：把指纹改成比明文，外部观测不到差别。我的 x4 用例证实日志和案件文件里既没有 Key 明文也没有指纹（M6b 下也是绿）。
5. **M12 绿**：把 `_resume_case` 的"内存里的任务不动"去掉后，没有用例变红。修 P2-A 时如果走 `_resume_case` 那条路，要防止把真正在途的页重置成待发送导致重发；所以建议走 `_next` 那条路，用 claimed 判断。
