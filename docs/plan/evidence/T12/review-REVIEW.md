## 一、问题清单

**P2-1 发送线程会永久死掉，队列静默停摆**
- **问题**：`queue.py` 里 `_worker` 的兜底处理本身会再出错。页处理出错后它调 `self._set_page(...)` 把该页改回待发送；如果出错的原因就是"案件文件夹不见了"或"case.db 被长时间锁住"，这一步会同样出错。异常就此跑出循环，发送线程退出，之后不会有任何线程替补。
- **影响**：任务停在 `running`，页停在 `sending`，没有暂停原因，界面看起来一直在识别。其他案件的任务也永远不再处理，直到重启服务。
- **证据**（都是我自己跑的）：
  - 真进程实验 `e_vanish`：A 案件文件夹被移走后，B 案件的任务 75 秒内一直是 `queued`，395 端 started=0。服务日志里两条 `ocr page fail OperationalError`。
  - 用例 `test_vanished_case_in_flight_kills_workers`：线程状态 `('ocr-0', False)`，B 停在 `queued`。
  - 用例 `test_long_db_write_lock_kills_worker`：另一个连接 `BEGIN IMMEDIATE` 占住 case.db 23 秒后，`ocr-0` 线程已死，任务 `running`，第 1 页停在 `sending`。调用栈指向 `queue.py:257` 的 `_set_page`，报 `database is locked`。
  - 现实触发：U 盘或网络盘上的案件被拔掉、文件夹被移走、case.db 被占住超过 20 秒。实测整案检索重建是一个写事务，12 MB 文本就占了 6.5 秒。
- **最小修复**：
  - `_worker` 的 except 分支里，`_set_page` 再包一层 try/except，只记日志。
  - `_process` 里取不到案件根目录时，把该任务移出内存，或标暂停后跳过。
  - 补用例：文件夹消失、长时间写锁。
- **归类**：范围内阻断（Spec 7.2/7.3 要求"恢复后自动继续"，任务所列的边界里明确有"盘拔"）。

**P2-2 一个案件读不了，所有案件的任务都排不上**
- **问题**：`_next` 按 job_id 依次打开每个任务所在案件的 case.db。只要排在前面的那个案件打不开，整轮挑选就抛异常；`_safe_next` 吞掉异常后返回"没活干"，后面所有案件的任务都轮不到。
- **证据**：用例 `test_vanished_queued_case_starves_others`。A 的任务在排队时 A 文件夹被移走，B 的任务 8 秒内一直 `queued`，发送线程活着但空转。
- **最小修复**：`_next` 里按任务逐个 try/except，跳过打不开的案件，可以给它标暂停。
- **归类**：范围内阻断，与 P2-1 同根。

**P2-3 作者的验收用例不稳定，全量会随机变红**
- **问题**：`test_resume_after_app_exit_without_resending_done_pages` 断言"最多重发一页"（`len(shas) <= 4`）。但发送是 2 路并发，退出时可能两页都在途，两页都会作废重发，于是是 5 次。产品行为是对的，是断言写错了。
- **证据**：
  - 我的全量运行里这条红了，`assert 5 <= 4`。
  - 单独连跑 12 遍，红 2 遍。
  - 作者 `pytest.txt` 自己也记了"一次未能复现的失败"。
- **最小修复**：这条用例设 `concurrency = 1`，或把上限改成 `3 + 并发数`。
- **归类**：范围内阻断。验收要求 pytest 退出码 0，用例不稳定就保证不了。

**P2-4 偏离③：主编排要求改，现状没改**
- **现状**：
  - `app.py` 里设置变化的回调只做 `st.net.update(...)`。
  - 探测线程 `_prober` 只恢复 `prep_down / offline` 两种暂停。
  - `key_invalid` 暂停的任务只有重启服务时，在 `_resume_case` 里被改回 `queued`。
  - 用例 `test_key_invalid_resumes_after_settings_put`：Key 换成有效值、`PUT /api/settings` 之后等 3 秒，任务仍是 `paused / key_invalid`。
- **缺口**：没有"写入设置后恢复因 Key 暂停的任务"的服务内部钩子。
- **最小修复**：
  - `st.settings.on_change` 再挂一个 `st.ocr.resume_paused("key_invalid")`：把内存里这类任务改回 `queued`，并唤醒发送线程。
  - 不改契约，补一条用例。
  - 另需确认：Host 存 Key 之后确实会调一次 `PUT /api/settings`，否则这个钩子触发不到（转 T13 / T20）。
- **归类**：范围内阻断（主编排的明确要求）。

**P3-1 作者的取消用例测不出"在途请求断开"**
- **证据**：变异 M1（取消时不断开在途请求）下，作者的 `test_cancel_keeps_done_pages_and_drops_in_flight` 仍然绿；只有我加的"发送线程 5 秒内回来"用例变红（实测 10.03 秒）。

  - 进程内实验里发送线程 0.08 秒内回来。

- **归类**：范围内，非阻断。

**P3-4 识别文本里若有一行恰好是"【第N页】"，会被当成页标记**

  - 再合并一次，统计变成 `pages:4`，文本不稳定，`is_ocr` 和页数统计会算错。
- **修复**：合并前把识别文本里与位置标记完全相同的行改写，比如行首加全角空格。
- **归类**：独立后续（T5 的 PDF 文字也有同样的问题，main 上 `51af385` 的修法只认"独占一行的标准标记"，挡不住这种情况）。

**P3-5 案件当时不在，回来后要重启才续做**

- **修复**：`case_open` 时对该案件调一次 `_resume_case`。
- **归类**：独立后续。

## 三、T5 三处改动

1. **`after_render` 挂钩**：只新增了 4 行：`__init__` 里一个属性，`_scan` 里写完文本、改完标题之后、保存 index 之前调用一次。既有逻辑一个字没改。只对本次重新解析成功的材料调用；单份材料合并出错时自己兜住，不让扫描失败。
2. **`stale_ocr`**：两种情形都对。
   - 原件没变、重新识别：两个任务版本相同，不算过期。
   - 原件改了：只有旧版本有已完成页时算过期；新版本有已完成页后清除；新版本任务还没完成任何一页时仍算过期。
3. **pdfium 锁**：
   - 锁的范围是"解析一整份 PDF"或"渲染一页"，没有把整次扫描串行化，其他类型的文件照常解析。
   - 压力实验：两个线程解析、两个线程渲染，各跑 20 秒。
     - 有锁：0 错误。
     - 去锁：2 万次 `corrupt / open` 误判，第 3 次直接崩溃，退出码 0xC000001D。
   - 所以这把锁也修好了 T5 原有的隐患：两个案件同时扫描 PDF 本来就会出错。
   - 代价：长 PDF 解析期间渲染要排队（实测 2628 次解析对 81 次渲染）。会变慢，但不会卡死。
4. **加锁顺序**：
   - 扫描：案件锁 → pdfium 锁 / sqlite / 检索锁。
   - 发送线程：`_cv` → sqlite；pdfium 锁单独拿；案件锁 → sqlite。
   - 没有任何地方持着 pdfium 锁再去拿别的锁。整理下来没有环，不会死锁。
5. **T5 既有用例**：全量运行中全部通过。

## 四、其余重点

- **超长识别文本（水印页重复输出）**：
