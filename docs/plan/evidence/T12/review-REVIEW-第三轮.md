## 一、问题清单

**P2（范围内阻断，触发止损）：收尾时任务已移出内存，再写库失败，任务永远停在 `running`**
- **问题**：`queue.py` 的 `_finalize` 依次做四步：
  1. 读状态；
  2. `with self._cv: self._jobs.pop(job_id)`，把任务移出内存；
  3. `_other_active`，然后 `_apply`（合并文本，`search_fts.refresh_after_scan` 也会写 case.db）；
  4. 最后 `UPDATE ... status = done`，库超时 10 秒。

  第 3、4 步抛错时，异常传到 `_worker` 兜底（或 `_finish_stuck`）。兜底只在已经不在内存的 Job 上设 `skip_until`，`_next` 再也遍历不到这个任务。新加的"补收尾"（`not rows and not job.claimed`）也走不到。
- **影响**：任务列表一直显示"识别中"，页数已满（例如 done 1/1），界面不会发"识别完成"通知。只有重开案件或重启才恢复。

  真实里能占住 case.db 的：同一服务里首次检索整案重建 FTS、扫描写 `material_ids`、其他任务收尾时的 FTS 刷新，以及外部进程。

  交付说明 P2-A 行写"`_maybe_finish`/`_finalize` 写库失败留下的……补一次收尾"，与事实不符。作者用例 `test_finalize_db_failure_then_job_still_finishes` 把故障注在 `_finalize` 入口，也就是移出内存之前，所以抓不到。
- **证据**（`scratchpad\rv-C18-T12-lab\test_lab_c18.py`，输出在 `lab-y.txt`）：
  - **y1（确定性复现）**：让 `_other_active` 抛一次 `database is locked`。12 秒后：`('running', 1, 0) {1: 'done'} in_mem False`，线程都活着。
  - **y2（真实锁）**：`_apply` 返回后另一连接 `BEGIN IMMEDIATE` 占 12 秒。放开 20 秒后：`('running', 1, 0) {1:'done'} in_mem False`，395 只收到 1 次请求。调 `/api/case/open` 后才变成 `done`。
  - 变异 A2、C2、C3 下 y1、y2 同样红（基线就红）。
- **最小修复**（二选一）：
  - 在 `_worker` 的 except 和 `_finish_stuck` 的 except 里，持 `_cv` 执行 `self._jobs.setdefault(job.job_id, job)`，把任务放回内存再退避；
  - 或者把 `_finalize` 里的 `pop` 挪到最后那条 UPDATE 成功之后。补收尾已有 `finalizing` 防重入，正常收尾时在途页也还在 `claimed` 里，所以挪了不会双收尾。

  另外收 y1、y2 为用例，交付说明那一句改成事实。
- **归类**：范围内阻断。`pop` 在前是此前既有（`ab43ba6`），但执行令点名的"同类：`_finalize` 库超时"没有关全。

**NOTE**
