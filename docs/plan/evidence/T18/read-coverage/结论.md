## "没读全"在服务端怎么算

- 在 `service\lawbench\case\task.py` 的 `TaskStore.coverage`，存草稿（`case_save_draft`）和任务结束（`/core/task/end`）时算，结果写进 `result.json` 的 `coverage`。
- 口径：只认 `reads.json` 里的读取记录，不采信模型自报。
  - `case_read_material` 每次成功读取，记下（材料编号、原件哈希、起止单元号）。
  - 对每份材料，把当前原件版本的读取记录合起来，算覆盖到的单元号，再除以材料文本的单元总数（页、段、行、表格行）。
- 会误判或让律师误解为"没读全"的情形：
  1. **还没识别**：整份没识别的，读取工具直接拒绝，记录为空，原来算"没有读"（本次已改为"读不了：还没识别"）。部分页没识别的，那几页是占位，不算读到，总数却照算，所以永远不会"读全"。这一条没改，只是如实，界面会显示"只读了 x / y"。
  2. **范围按全案算**：覆盖清单遍历本案全部材料，不是这次任务的范围。律师只让读其中几份时，其余的也会算进"没读全"，界面却写"本任务范围内 N 份"。改要让服务知道范围（任务单或必问答案），属契约 1.4 候项。
  3. **分段读**：单元超过 8000 字时用 offset 分段读，只有从 0 起连续读到单元末尾才算读了这个单元；从中间开始读的永远不算。
  4. **读完后原件改过**：重新扫描后原件哈希变了，旧的读取记录作废（这是设计如此）。
  5. **识别空白**：395 返回空文本的页不是占位，算读到了，内容为空（本次没遇到）。
