# Reviewer A（改动纪律与可维护性）：T17 活着的句柄（N54 ①），target `0210476`

结论：线 A 的改道判断是对的，也确实修好了复核员 B 那几种情形：B 的三份实验原样跑，Y1、Y1m、AG 都变成"落新位置、旧处不变、重启看得到"。但我在独立实验里发现了两种本轮引入的新问题：一种是静默丢失，另一种是会话被永久卡死，叫律师照做也解不开。另外，用真服务的规则去看，"活会话复制后接着写落新文件夹"这个主结论并不成立。所以给 AMEND。

## Findings

**P2-1 搬写入者的那几十毫秒里，律师发的话会静默丢，而且之后整个会话都写不进去（本次引入的回归）**
- 问题：`router.ts` 的 `relocateOnce` 先关旧句柄（旧实例里注销写入者），然后才 `locate`、在新位置 `open(id,'write')`、读两份记录、补齐。这段时间里两个实例都没有登记写入者，DSH 的 `session/event` 投给 `writers.get(id)?.` 就直接丢掉（`storage.ts:535–539`）。核对用的 `expectedEvents` 是搬之前取的 `seq`，所以照样判"已搬"。
- 实验：复制后调 `caseOpen`，不等它完成，过 N 毫秒在这个活会话里发一句，连跑两遍结果一致：
  - 0、5、10、80 ms：正常。
  - 20、40 ms：这一句新旧两处都没有，`writerLost=false`，Agent 插件不拦、界面不提示；接下来再发一句也哪里都没有，`flush()` 报 `AggregateError`（只在内部）。从那一刻到关软件，这个会话全部静默丢失。
- 影响：正是 F1 要消灭的那种失败。触发要碰上时间窗；窗口长短取决于逐个案件根 stat（每个最多 3 秒）和读两份完整 JSONL 的时间。
- 最小修复：换上新写入者之后，再拿内存里的 `seq` 对一次。短了就把差的事件补上（或记为已失效，让下一轮拒绝）；或者在搬的期间用 `agent/pre-step` 暂拒新的一轮。

**P2-2 名单刷新时新位置还没列出来，会话就被永久记为"已失效"；界面让律师"重新打开案件"，照做也没用（本次引入）**
- 问题：`relocateOnce` 找不到新位置时先关旧句柄、再 `lose('not_found')`。`lost` 一旦为真就不再解除：`staleWriters()` 过滤掉 `w.lost`，`relocateOnce` 遇到 `w.lost` 直接返回。还有一点：`writerStale` 只要 `existsSync(案件根)` 为假就算失效，而侧栏每次 `list()` 都会在后台刷新名单（5 秒节流），每次刷新成功后都会触发 `relocateStale`。
- 实验：
  - E1：搬家后先来一次后台刷新，再在新位置 `caseOpen`：打开前后都是 `lost=true`，续写新位置不变。真实使用里律师在资源管理器搬完、回到首页点"进入"之间，很可能先有一次刷新。
  - E2：案件文件夹暂时不在（改名又改回，类似网络盘掉线）期间刷新一次：文件夹回来、再打开，仍是 `lost=true`，续写没落盘。修前这种情况写入者会自己重试恢复。
- 影响：这个对话本次运行里每一轮都被拒。`CASE_MOVED` 的提示写"请从首页重新打开案件，再在这个对话里继续"，在所有已失效的情形下这条路都走不通，只有重启才行。交付说明 9.5 只写了"两处分叉"这一种，没写搬家或盘暂时不在。
- 最小修复：先 `locate`，再 `open` 新位置，都成功了才关旧句柄。找不到新位置时不标 `lost`，保留旧写入者，下次刷新再试。提示文字改成与实际一致（需要重启就直说）。

**P2-3 用真服务的规则看，活会话复制或搬家后，在新位置打开也续写不了，整轮被拒（此前就有；但它推翻了本轮"续写落新文件夹"的结论，算范围内阻断）**
- 问题：写入者搬过去了，但活 Agent 内存里会话记录头的 cwd 仍是旧位置。我方 Agent 插件拿 `agent.session?.header?.cwd` 调 `task/begin`（`agent/index.ts:69–71`）。真服务在新位置打开后按 case_id 去重，只留新根（`registry.py:136–138`）；`find_by_root(旧 cwd)` 返回 `CASE_NOT_FOUND`，于是整轮被拒。
- 证据：
  - E4：搬过之后 `agentCwdIsOld=true`、`sessionsCwdIsOld=true`。复核员 B 的 AG 输出里同一行也写着"session cwd <tmp>\桌面\案丙"。
  - 我用真 `CaseRegistry` 跑：打开旧位置、复制、打开新位置之后，`find_by_root(旧) → CASE_NOT_FOUND`，最近案件只剩新位置。
  - 交付说明 9.6 的桌面端"续写落新文件夹"是在开发假服务上测的，假服务的 `task/begin` 不核对 cwd（`fake-service.mjs:84–92`）。截图 01 里这个活会话的右栏显示"这个会话所在的文件夹还没作为案件打开"，输入区显示"先打开或新建一个案件，再在这里发消息"，复测记录和 9.5 都没提。
  - `live-writer.spec` 里没有 Agent 插件，覆盖不到这一层。
- 影响：律师实际看到的是"消息发不出、提示先打开案件"，打开了也一样；没写旧处、没静默丢，但和交付说明的结论不符。
- 最小修复：Agent 插件调 `task/begin` 时传会话当前所属的案件根（向会话存储取 owner，不用内存记录头），界面判断会话属于哪个案件也照此改。做不到就把这条如实写进已知限制，提示改成"重启后继续"。

**P3-1 名单刷新路径上有同步的 `existsSync(案件根)`（臆测，未实测）**：`writerStale` 每次刷新成功都对每个活写入者做一次同步 `existsSync`。网络盘挂住时会卡住 Host 进程，绕开了 B-F5 的 3 秒上限。改成走带上限的异步 stat。

**P3-2 会话被 DSH 收掉时，我方的写入者记录不清（臆测）**：DSH 收掉会话时直接关原始句柄（`storage.ts:548–553`），不经路由代理的 `close`，所以 `router.writers` 里会留一条，`waiting` 里的监听也一直挂着；之后刷新可能为已收掉的会话在新位置开一个写句柄。

**NOTE**：PATCHES.md 新的那一行没登记两条本轮实际依赖的行为：被拒的一轮仍会往内存会话里追加事件（E3：`seq` 从 11 变 15），以及活 Agent 的内存记录头不随存储刷新。

## 改道的机制判断
- ① 活会话写记录不经句柄 `append`：核实。原版实例 `install()` 里监听 `session/event`，按会话编号投给 `writers`（`storage.ts:534–554`）；`close` 先落盘再注销，`open` 写方式时登记写入者。
- ② Agent 外面放不下：核实。`AgentHandle.dispose` 只在创建者手里（`core/agent/src/index.ts:146–163`），会话控制器 resume 后只返回 `.agent`（`session-controller/src/agent.ts:437/469`）；`seq` 等于内存事件数（`core/session/src/index.ts:681`）；Agent 状态只有 `idle` 和 `running`。
- ③ 每步失败的退回路径：打开失败、两处分叉、比内存短都会记为已失效，不写旧处。但"先关旧句柄"带来 P2-1 的时间窗和 P2-2 的永久失效。
- ④ 补齐逻辑：按事件位置取前缀，再整份 JSON 比对。在"等这一轮结束再搬"的路径上不漏不重（E6 排队一句也正确）。问题在空闲时那段搬迁窗口（P2-1）。
- ⑤ `CASE_MOVED` 复用了 T13 同一套 `noteBlocked`/`turnNotice` 机制，没有另写一份。
