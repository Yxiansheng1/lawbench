真服务不是这样：要等律师在新位置执行一次打开案件（`caseOpen`），服务才改为只列新位置（`registry.py` 的 `open` 和 `recent`）。

## Findings

### F1 · P2 · 范围内阻断：复制或搬家后，第一次在新位置打开案件，旧会话不挂回；这段时间续写进旧文件夹（B-F2 与 B-F1 同根因再露）

**问题**：名单只在两个地方刷新。
- 列表（`router.ts:308`）：不等结果，5 秒内不重复问。而且 `all()` 在刷新回来之前就取了名单。
- 新建（`router.ts:228`）：强制刷新。

打开案件的流程不刷新名单：`ui\cases.ts:33` 先 `caseOpen`，接着 `openCaseWorkspace` → `workspaces.create` → `attachCaseSessions` → `persistence.list()`。这时用的还是旧名单，交出的 cwd 是旧根，筛出来要挂的会话为 0。

**影响**：

| 情形 | 现象 |
|---|---|
| 复制 | 旧会话仍挂在旧位置的工作区下 |
| 纯搬家 | 旧会话进"未分组" |

以上都要等律师再打开一次该案件才归位。另外，在名单换过来之前打开旧会话续写，写进的是旧文件夹；名单换过来以后，这段内容在新位置"看不见"。这正是 B-F1 要防的事。

**证据**：用例 `zz-rvb21.spec.ts`，真 JSONL 实例、真 `WorkspaceRegistry`、真名单刷新，127.0.0.1:19311 上起一个假服务，按真服务语义做到"`caseOpen` 之后才只列新位置"。
- X1 复制，两种时机（5 秒节流内、距上次刷新超过 5 秒）都是：
  - 第一次挂回结果 `{"attached":0,"failed":0}`，新工作区 `[]`，旧工作区 `["s1"]`；
  - 名单刷新后、再打开之前，仍然是新 `[]`、旧 `["s1"]`；
  - 第二次打开才得到 `{"attached":1}`，新 `["s1"]`、旧 `[]`。
- X1b 纯搬家：启动后名单为 `[]`，第一次挂回 0；会话已列出、cwd 是新位置，但新工作区成员为 `[]`（未分组）；第二次打开才挂上。
- X10：复制后，在新位置执行 `caseOpen`，1.5 秒后 `open('s1','write')`：
  - 句柄 cwd 是 `<tmp>\桌面\案丙`（旧位置）；
  - 续写后旧文件夹变了，新文件夹没变。

**最小修复**：`caseOpen` 成功后、`attachCaseSessions` 列表之前，强制刷新一次名单并等它回来（上限 3 秒）。可以由 Host 在 `callApi('caseOpen')` 成功后通知会话存储，也可以给会话存储加一个 `refreshCaseRoots(force)`，挂回前先调。`open`/`stat` 哪里都找不到时，也强制刷新一次再找。

**回归**：用"`caseOpen` 之后才改返回"的假服务、不重启，在同一进程里断言：
- 第一次打开就挂上；
- 续写落在新文件夹，旧文件夹字节不变。

**归类**：范围内阻断。冻结清单 B-F2 的根因（打开新位置时没把旧会话挂过去）在真实流程上仍在。

### F2 · P2 · 本次引入的回归：去掉旧工作区那一步失败、或私有字段 `table` 不在时，照样挂到新工作区，同一编号记在两处，下次启动工作区服务起不来

**问题**：`attach-sessions.ts:42-50` 的处理有两个漏洞。
- `detachSession` 抛错时只记日志，接着照样 `attach`。`detachSession` 不存在时（`?.`）也一样。
- 私有字段 `table` 不在、`indexHeaders` 还在时，退回看过滤后的 `sessionIds`。重建索引后，旧工作区已经不"算"这个会话，于是根本不去 detach。

**影响**：DSH 启动时 `validateStoredState` 发现同一编号记在两个工作区，抛"workspace domain is inconsistent"，整个工作区服务（连同侧栏会话）起不来。这是作者桌面端已经碰到过的坏状态，而且没有自愈，只能手工改登记文件。

作者说"私有依赖不在时只记日志、登记不被破坏"，对"`table` 不在、`indexHeaders` 在"这种情况不成立。

**证据**（X2，两种情况结果相同）：
- 挂回结果 `{"attached":1,"failed":0}`，新、旧两个工作区的原始记录都是 `["s1"]`；
- 重启报 `workspace domain is inconsistent: session 's1' is accounted by both workspace … and workspace …`。

**最小修复**：
- 某编号的任何一次 detach 失败，就不挂它，计为失败；
- 拿不到 `table` 原始记录时，不挂"可能还记在别处"的会话（或者 indexHeaders 也一并不调）。
- 补这两种情况的用例。

**归类**：本次引入的回归（B-F2 返修带入）。

### F3 · P3 · B-F6 在原复现上仍失败

**归类**：范围内（与 F1 同根因）。

### F4 · P3 · 活性：名单为空、服务又一直没起来时，每次列表和新建都等满 3 秒

**证据**：X5，连续三次 list 分别耗时 3002、3013、3009 ms；新建耗时 3003 ms，提示是"服务还没就绪"（正确）。

**影响**：服务起不来（配置坏、崩溃）期间，侧栏每次刷新都卡 3 秒。有上限，不会挂死。

**修复**：首刷只等一次；或者只在服务处于"正在启动"时才等。

**归类**：范围内（B-F4 带出的副作用）。

### F5 · P3 · 独立后续：单个案件根挂住时，`flush` 没有上限

**证据**：X6。
- 挂起的根上，`list`、`stat`、`open` 都在约 3 秒时跳过，日志只记序号和 `ETIMEDOUT`；

原版构造函数里同步的 `readdirSync`（上一轮的 NOTE）也还在。

### F6 · P3/NOTE：服务成功返回空列表时，名单整个清空

**触发**：`cases.json` 丢了，或换了服务数据目录。

**影响**：所有案件会话从列表里消失；律师重新打开某个案件后，那个案件的会话能补回来（X3，经第二次打开或新建）。另外，复制后只在旧副本里写过的会话，换成新位置后看不见。文件还在，只是不列。

**建议**：作为已知限制写进交付说明，或者空列表时保留旧名单。
