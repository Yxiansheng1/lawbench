### F1 · P2 · 范围内阻断：案件文件夹复制到新位置后，会话仍从旧副本读，续写也写进旧文件夹
- **问题**：
  - 真服务 `registry.open` 按 case_id 去重，只留新位置一条；`recent()` 列出注册表全部案件（不限条数，`service/lawbench/case/registry.py:110-117`），**旧位置根本不出现**，也就不会有 `exists:false`。
  - `case-roots.ts` 的 `merge` 规则是"没列出的保留"，所以旧根永远留在名单里，而且排在前面。
  - 路由 `list`、`locate` 按名单顺序先到先得（`router.ts:128-135`、`166-173`），同一编号在新位置那份被当成重复丢掉。
- **影响**：
  - 律师在新位置打开案件，看到的会话 cwd 是旧路径，续写写进旧文件夹（比如桌面上那份）。
  - 之后旧文件夹一删，会话就退回复制那一刻的状态，这之后写的内容"看不见了"。
  - 这正是 Spec 4.1 说的"会话记录在案件目录内，跟着一起走"要防的事。
- **证据**：
  - E2，真原版 JSONL 包经我方插件。复制后按真服务语义只报新位置：名单变成 `[<tmp>\桌面\民事-虚构乙, <tmp>\案件盘\民事-虚构乙]`；`list` 交出 1 行，cwd 为 `<tmp>\桌面\…`；写句柄 cwd 也是旧路径。续写后旧文件夹 1318 字节，新文件夹仍是 503 字节。
  - W3，真 `WorkspaceRegistry`：新案件工作区 `sessionIds=[]`，旧工作区 `=[s1]`。
  - 作者的搬家用例（`session-store.spec.ts:208`）喂的是 `{旧根, exists:false}`，真服务从来不会这样返回，所以没测到这条路。
- **最小修复**：刷新成功时以服务返回为准，名单换成 `exists:true` 的那些根；只有刷新失败才保留旧名单。
- **回归要求**（作者加，要对称）：
  - 复制场景：旧文件夹还在、服务只报新位置 → `list` 的 cwd 是新根，续写落在新文件夹，旧文件夹字节不变；
  - 纯搬家照常能列、能开、能续写；
  - 盘拔了（`exists:false`）去掉，插回来（`exists:true`）加回。

### F3 · P2 · 本次引入的回归，候主编排裁决：关掉会话投影缓存后，每次重启侧栏会话全没标题

### F4 · P3 · 范围内：名单缓存为空或读坏、服务又还没起时启动
- **现象**（E1、W2）：
  - 案件里的旧会话不列出，按编号打不开（`SessionPersistenceNotFoundError`）。
  - 在案件里新建，被拒绝，提示却是"这个文件夹还没有作为案件打开"，误导。
  - 更重的后果：工作区登记启动时建的会话索引缺了这些会话。随后在该案件新建一个会话（此时它是活会话，`attachSession` 不重新列表，直接 `mutate` 剪枝），旧会话被**永久移出**案件工作区。W2：`[s2,s1]` → `[s3]`，再重启仍是 `[s3]`。
- **触发条件**：少见。缓存文件丢失或损坏（`load` 把坏缓存当空）。
- **最小修复**：二选一。
  - 缓存为空、而工作台服务存在但还没进 running 时，第一次 `list` 有上限地等第一次刷新；
  - 或者服务不可用时换一句说明，比如"工作台服务还没就绪"。

### F5 · P3 · 独立后续（活性）：某个案件根读取挂起时没有超时
- **现象**：
  - E6：假实例 `list` 永不返回，`router.list()` 2 秒后仍挂着。
  - 工作区登记启动时要等 `list`（`workspace/src/index.ts:196-216`），会跟着一起挂住。
  - 原版实例的构造函数用同步的 `readdirSync` 检查根目录（`jsonl index.ts:1505`），在映射网络盘上会卡住整个 Host 的事件循环。
- **已排除**：名单刷新本身有上限。E7：服务不回应时，`list` 最多多等 3004 ms，5 秒节流；案件外新建每次 3 秒后拒绝；没有无限重试。
- **最小修复**：每个案件根的 `list`、`stat` 包一层超时（比如 3 秒），超时就跳过并记元数据日志。
- **说明**：真实 SMB 超时的时长没有实测，属臆测。
