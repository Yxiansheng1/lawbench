**"删掉会不会误删"：**
- 只有当测试前读到"没有 Key"时才会去删 Key，只有当测试前 `settings.json` 不存在时才会删文件，删的都是这次测试自己写的东西。
- 删失败会报出来（E2、E4、E5）。
- 唯一的误判来源是缓存给出过期值（H1）。

**读旧 Key 失败：** `readKey` 失败会抛错，不会返回"没有 Key"，所以什么都不改（F1）。

**凭据缓存改动对取 Key 的其他调用方的影响：**
- 写入失败后缓存为空，下一次 `resolve` 会回到凭据管理器读实际的值，拿到的是真值，不会拿错。
- 代价只是多一次读；如果这次读也超时，调用方会拿到报错。
- 唯一"拿错"的情形是 H1 那种并发交错。

## 三、Findings（按严重度）

**P2-1 · 此前既有（"先保存再测"的设计，来自第一次返修 5bce1c3）· 落在本卡旅程上 · 触发主编排的止损线：测试进行中进程被结束，输错的配置会被静默保留**
- **问题**：新地址、新 Key 先落盘，再去测。测试和恢复都在 Host 进程内存里完成。进程在这个窗口里被结束，就不会有恢复，也没有任何记录。
- **证据**：实验 `crash-exp.mjs` 用构建产物 `lib/host.js` 在子进程里跑 `trialConnection`，连接测试用一个不回应的本机端口拖住，1.5 秒时结束子进程。
  - 测试前已有配置：`settings.json` 的 `llm_base_url` 变成 `http://llm.invalid:8000/v1`，Key 变成输错的那个。
  - 首次配置：结果相同，下次启动 `configured=true`。
  - 对照组（不结束进程）：30 秒后显示"工作台服务未启动，请稍后重试；已恢复为测试前的配置"，地址和 Key 都回到原值。
- **影响**：
  - 用户在测试没跑完时关掉窗口或程序（连不上时测试要几秒到几十秒），或者程序崩溃、Windows 关机，都会触发。
  - 结果是存好的正确 Key 被输错的覆盖，这正是 P3-5 要防的；或者首次配置时没验证过的配置被当成"已配置"，下次首次配置页被跳过。
  - 目前产品里没有别的地方能改地址（P-13 关掉了打开配置文件），要等到 T13 有了设置页才能改。
- **最小修复（二选一）**：
  - 一是主编排已列的方案：改契约，让测试直接带候选地址和 Key 去测，不先保存。
  - 二是开始前在应用数据目录写一个"测试进行中"标记（不含机密），通过或恢复完成后删掉；启动时看到标记，`setupState` 返回未配置，页面提示"上次测试连接没有完成，地址和 Key 可能已改变，请重新填写"。

**P2-2 · 臆测（触发条件）；机制已由实验确认，主要来自此前既有的缓存设计，本次"写前作废缓存"又把窗口稍微扩大了一点：并发读取留下过期缓存，第二次测试把输错的 Key 当"旧值"写回去**
- **问题**：`LawbenchCredentials.current()` 把读到的值放进 5 分钟缓存，但不管读取期间有没有发生写入。
  - 如果一次读取在新 Key 写入之后开始、在恢复写回之后才返回，缓存里就留着输错的 Key，凭据管理器里却是原值。
  - 5 分钟内再测一次，`trialOnce` 从缓存拿到的"旧 Key"就是输错的那个，失败后把它写回凭据管理器，页面却显示"已恢复"。
- **证据**：实验 H1。第一次测试后凭据管理器是原值、缓存给出新值；第二次测试后凭据管理器变成第一次输错的值，第二次的 `restored=true`。在复原后的代码上也是红的。
- **为什么说触发条件是臆测**：
  - 首次配置期间还没进入工作区，页面在测试进行中禁用按钮。
  - DSH 的 `llm-pi-ai` 只在发模型请求时才取 Key（`packages\llm\llm-pi-ai\src\index.ts:194-196`）。
  - 所以我没找到会在测试期间并发读 Key 的调用方。
- **本次改动的影响**：旧写法下，写入进行中的读取会直接命中缓存；现在写之前先清缓存，写入期间的读取会去读凭据管理器，读到写之前的值又晚于写入返回时，缓存就过期了。
- **最小修复**：在 `LawbenchCredentials` 里加一个写入计数，`set`/`unset` 时加一；`current()` 只在读取期间计数没变时才写缓存。约 3 行，另加一个用例。
