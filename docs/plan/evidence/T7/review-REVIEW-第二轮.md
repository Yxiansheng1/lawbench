## 二、Findings（按严重度）

**F1 · P2 · 冻结清单内未关闭（P3-5 的错误路径）：恢复失败时 Key 不恢复，用户也不知道**
- **问题**：恢复逻辑写在 `host\index.ts:152-158` 的 `finally` 里，四步顺序执行，任何一步抛错后面都不再执行：
  1. 先 `putSettings(oldSettings)`（要经过服务）；
  2. 再 `cred.set` / `cred.unset` 恢复 Key。

  如果第 1 步抛错（比如服务在测试中途挂了，或正被看护重启，这时 `endpoint()` 返回 undefined），恢复 Key 这一步就不执行了。反过来，设置恢复成功、Key 写入超时，就留下"旧地址 + 新 Key"。无论哪种，页面只显示一句"工作台服务未启动，请稍后重试"或"凭据管理器操作超时"，不说配置已被改动。
- **证据**：我在实验目录写了用例 E1：已有设置和旧 Key，从第 3 次调用起让端点消失。结果：
  - 抛出"工作台服务未启动，请稍后重试"；
  - Key 变成了测试时输错的那个；
  - `settings.json` 里的 `llm_base_url` 仍是新填的 `http://llm.invalid:8000/v1`。
- **影响**：
  - 测试时输错的 Key 会覆盖存好的正确 Key。首次配置时可能改了地址，但因为 Key 已存在，下次启动不再显示首次配置页。
  - 真服务如果在连接测试期间卡住，导致 `/health` 连续 3 次没响应，看护会杀掉并重启服务，正好触发这条路径。这一点是推断，要等 T8 用真服务核实。
- **最小修复**：
  - 设置和 Key 各自单独 try，一个失败不影响另一个；
  - 任一步恢复失败，就抛一条明确的中文提示，例如"测试未通过，且未能恢复原配置，请重新填写后保存"；
  - 补一个"恢复时服务不可用"的用例。
  - 不改契约。

**F2 · P3 · 独立后续：两次"测试连接"并发会留下输错的配置**
- **问题**：`trialConnection` 没有互斥。第二次调用会把第一次刚写进去的新值当成"旧值"读走，第一次恢复完以后，第二次又把错误值恢复回去。
- **证据**：实验 E2b，两次失败的测试错开 60 或 80 毫秒发起，最后 Key 是 `sk-typoA-…`，地址是 `.invalid`；错开 20、40、100 毫秒时结果正常。
- **影响有限**：页面在测试进行中会把两个按钮都禁用（`WelcomePage.tsx` 的 `disabled={loading || busy !== ''}`），正常界面点不出来，只有第二个调用方（比如另一个窗口或别的插件）才会触发。
- **最小修复**：在 `LawbenchRemote` 里用一条 Promise 链把 `trialConnection` 串起来。

**F3 · P3 · 此前既有：首次启动失败时状态卡在 starting**
- `apply()` 里 `supervisor.start().catch(...)`（`host\index.ts:210`）只记日志，不把状态设为 failed。P3-2 只修了 `onExit` 里的两处重启调用。
- 首次挑端口就抛错（例如端口范围全被占）时，状态会一直停在 `starting`。
- 最小修复：这里也把状态设为 failed，或者让 `start()` 走 `relaunch`。

**F4 · NOTE · 本次返修引入：stop() 之后状态可能被改成 failed**
- `relaunch` 的 `.catch`（`supervisor.ts:173-176`）不看 `stopping`。如果 `stop()` 之后 `pickPort` 才抛错，状态会从 `stopped` 被改成 `failed`。
- 之后再 `start()` 能恢复，不会卡死。修法：catch 里加一行 `if (this.stopping) return`。

**F5 · NOTE：`safe()` 的中文过滤没有测试兜住**
- 冻结要求的"远端错误不含中文就换成通用文案"已经由 `invoke` 那一层的用例覆盖，变异 D6 能抓到。
- 但 `safe()` 的第二道过滤（`welcome-backend.ts`，针对 fetch 失败、JSON 解析失败这类本地异常）被放开后测试仍绿（变异 D7）。它是兜底的第二层，所以不阻断。

**F6 · NOTE：不改 Key 也会重写一次旧 Key**
- 用户没改 Key（`key === null`）、测试又没通过时，恢复逻辑仍会经 PowerShell 把旧 Key 重写一遍。没必要，还多一个可能超时的环节。
- 修法：`key === null` 时跳过 Key 的恢复。

**F7 · NOTE / 臆测：两处要等真服务核实**
- 测试前没有 `settings.json` 的情况，恢复时 Host 直接删文件（`rmSync`）。如果真服务在内存里缓存了设置，删文件后服务端可能仍用着新地址。
- 桌面端经网关调用 `lawbench/trialConnection` 的端到端链路没有实测，作者也写了"桌面端界面未重新截图"。我核过静态部分：网关按参数名映射参数，而 DSH 的 lookup 提供者只有 `session`、`agent`、`workspaceFileScope` 三个，和 `servers`、`key` 不冲突，推断能正常调通。
- 这两处都放到对真服务复测时一起核实。
