# 上下文压缩与"加载技能"死循环 · 排查报告（2026-10-11）

令 `致A-ORCH-执行令-P0-技能加载与上下文压缩死循环-20261011-0329.md`、注记 `…-追加-任务结束清Skill选择与压缩循环排查-20261011-0329.md` 第 2 条、注记 `…-P0追加线索-压缩后老问题复活-20261011-0342.md`。
用户那台机器的日志（`D:\lawbench-coord\附件-用户日志-20261011\`）写报告时还没有放进来；下面的根因是对着 DSH 源码和我方配置算出来的，并在本机真机上验证了改后的行为。

## 结论
三件事叠在一起，都在 DSH 的上下文压缩（`compaction-basic`）上：

1. **压缩触发得太早**（主因）
   - DSH 的触发点 = min(窗口 × 0.8, 窗口 − 本次请求的 max_tokens − 预留 `headroomTokens`)，`headroomTokens` 默认 65536。
   - 我方按 Skill 的 `max_tokens` 发请求，窗口 131072：

     | 请求的 max_tokens | 哪些 | 原触发点 | 占窗口 |
     |---|---|---|---|
     | 16384 | 自由对话、刑期计算等 4 个 Skill | 49152 | 37% |
     | 32768 | 合同审查等 6 个 | 32768 | 25% |
     | 49152 | 辩护词、诉讼文书等 7 个 | 16384 | 12.5% |

   - 用户截图右下角 **52K/131K（40%）** 正好越过 49152：从那以后每一步模型调用之前都压缩一次。
   - 和 Skill 的 `window`（64K / 128K）没有关系——`window` 只管服务往任务输入里放多少，不参与这个算式。所以**不用改 Skill 的 window**。
2. **压缩把前面的内容换成一段摘要，摘要又让模型"接着做"**（循环的直接原因）
   - 压缩保留最近约 1.8 万 token，把更早的（案件卡片、任务输入、已加载的技能、读过的材料）换成一段英文摘要。
   - 摘要里有"Pending Jobs""Next Step"两节，插回对话时开头语写的是"从后面的消息接着做"。没答完的那句"那他至少需要判多久"就成了每次压缩后的固定任务：模型重新想同一句话 → 技能内容已不在 → 再加载 → 又越过触发点 → 再压缩。
   - 之后只发"你好"也一样：摘要里的老问题排在前面，模型先去办它。
3. **压缩一触发，先把大的工具结果剪掉中间**
   - 超过 8192 字的工具结果只留头 4096、尾 1024。一次读满 8000 字的材料转成 JSON 文本后超过 8192，会被剪成约 5000 字——"没读全"的另一个来源。
   - 各 SKILL.md 全文 3400 到 5800 字，本来不会被这一步剪（最初的判断"剪枝把技能结果剪掉"不成立；技能是被第 2 条的摘要换掉的）。

## 几个问题的回答
- **压缩调用计不计入 16 次预算**：不计。压缩是 DSH 自己在每步之前做的，写摘要的那次模型调用不经过我方计数。但每一圈里模型"想一句、加载技能"的那次调用是计的，所以 16 次很快用完。
- **自由对话一句话近 5 分钟**：同一个原因。上下文越过触发点后，每一步之前都要先做一次压缩（一次完整的模型调用，输出最多 6.5 万 token 的额度），压完仍在触发点之上还会再试一次；一步变成两三次模型调用，而且每圈都在重读。
- **点胶囊时 SKILL.md 在不在系统提示里**：不在。系统提示只有通用规则和技能目录；SKILL.md 全文是模型调"加载技能"读进来的一条工具结果，所以会被摘要换掉。

## 改法（一个提交，见 `evidence\T13\交付说明.md` 末节）
1. 组合包 `dsh-ext\cordis.patch.yml`：`compaction-basic` 设 `headroomTokens: 16384`、`maxTokens: 8192`（摘要自己最多写 8192）、`thresholdRatio: 0.8`。触发点变成 98304 / 81920 / 65536（窗口的 75% / 62% / 50%）。（初版预留 8192，复核 rv-A62 P2-2 指出 DSH 按 4 个字符 1 个 token 估、中文少算，余量太小，改为 16384。）
2. 同处：剪枝门槛 8192 / 4096 / 1024 改为 48000 / 32000 / 8000，一次读回的材料不再被剪。
3. DSH 补丁 **P-25**：摘要插回对话的开头语后面加一句"检查点里都是历史，当前请求是之后最新的那条用户消息"；写摘要的要求加一条"待办和下一步只列最近一条用户消息要求的事"。
4. Agent 插件：
   - 每轮注入的案件卡片、任务输入放到律师消息**之前**，模型看到的最后一条用户消息是律师刚发的那句。
   - 防循环兜底：同一任务里同一个技能最多加载 3 次，第 4 次拒绝并告诉模型不要再加载（日志 `agent.skill_reload_loop`）；连续 3 次压缩之间都没有新的案件工具调用（没读新东西、没存稿）就存稿收尾（日志 `agent.compaction_loop`）；有进展的压缩不计，正常的长任务不受影响（复核 rv-A62 P2-3 改的口径，初版是"压缩超过 3 次"）。

## 验证
- **用例**：`dsh-ext\tests\compaction-loop.spec.ts` 10 项。触发点、剪枝都是引 DSH 自己的源码算的（根因两例、改后两例）；重放真机那个循环——原来转满 16 圈，现在连续 3 次没有进展的压缩后存稿收尾，共 3 圈。
- **真机**（开发版接本机真服务和 6000D 所外地址；案件用 `tests\fixtures\criminal-01`，没有生成 wiki，2 份材料待识别）：
  1. 自由对话问"那他至少需要判多久"：约 1 分钟、10 步答完，没有加载技能的循环，没有压缩，存了草稿"量刑分析"（截图 1）。
  2. 同一会话接着发"你好"：1 步，答的是你好（截图 2）。
  3. **把触发点临时压到 2600 token**（让每一步都压缩，模拟用户那台机器的处境），另一个同样问过那句话的会话里发"你好"：会话记录里这一轮先压缩了一次，摘要的"待办"写的是"无"，用户消息的顺序是 检查点 → 案件卡片 → "你好"；模型 1 步答了你好（截图 3）。检查点里带着 P-25 加的那句话。临时改动已还原。

## 没做到的
1. **没有在本机复现出改之前的循环**：本机这个测试案件上下文只有一两万 token，到不了原来的触发点（49152）；用户那边是连着跑了两个任务、上下文到 52K 才出现的。"改之前"的样子以用户的截图为准，本机只有用例重放。
2. **没有对着用户日志核**：日志还没到。到了以后可以核两点：每圈压缩的触发原因是不是都是"越过触发点"；有没有"压完仍在触发点之上"的告警。
3. **`max_tokens` 为 49152 的 7 个 Skill，触发点只能到 50%**（窗口 − 49152 − 16384）：预留给输出的太多。要到八成得把这些 Skill 的 `max_tokens` 降到 16384 左右，属于 `skills\`（线 B），请定。
4. **摘要是英文、按"编程助手"的口吻写的**（DSH 原文）：这次只加了两句，没有整段改成中文法律场景。触发点放回去以后压缩很少发生，先不动。
5. **"刑期计算"胶囊这次没有单独跑**：它的 `max_tokens` 和自由对话一样是 16384，走的是同一个触发点；真机第 3 步的会话就是模型自己加载了 `sentence-calc` 的那一个。
