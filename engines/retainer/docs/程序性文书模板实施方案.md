**编制日期**：2026-09-16
**目标**：按评估报告推荐方案（独立文件夹、零代码改动、只用工作台现有占位符）实施 25 份程序性文书模板
**前置状态**：工作台 3.4.1，10 项缺陷已修复并回归通过
**本文档性质**：实施前的方案讨论稿，用于确认关键选择并锁定风险控制措施。确认后按第八部分步骤执行。

## 一、实施范围与边界

### （一）本次做什么

1. 新建顶层目录 `procedural-templates/`，含 25 份 DOCX 模板与 1 份说明文件。
2. 建立生成脚本 `tools/build-procedural.cjs`，可重复生成全部模板。
3. 建立校验脚本，对生成结果执行结构、占位符、版式三类自动检查。

### （二）本次明确不做

| 不做的事项 | 理由 |
|---|---|
| 不修改 `app/` 下任何运行代码 | 零代码改动是本方案的核心前提，代码不动则功能不回退 |
| 不修改 `data/config.json`、`data/rules.json` | 一旦修改即触发版本校验链，且新增字段会撞上“本版不支持增加案件字段”硬断言 |
| 不修改 `resources/templates/` | 该目录由构建脚本清空重建，非构建产物不得放入 |
| 不新增或重命名占位符 | 超出 19 个白名单的占位符会被工作台拒绝 |
| 不改动 `tools/build.go` 与 `tools/build.cjs` 的扫描范围 | 二者只遍历 `original-skill/` 与 `docs/`，新目录天然不被触及 |
| 不把新模板导入工作台的模板库 | 模板库存储于浏览器，导入会产生副本与备份负担；按需导入即可 |

## 三、DOCX 生成技术方案

### （一）三项前置核查结果

| 核查项 | 结果 | 对方案的影响 |
|---|---|---|
| 托管 Python 是否含 python-docx | 缺失 | 不作为生成工具 |
| 系统 Python（`C:\Python314`）是否含 python-docx、lxml | 均具备 | **用作校验工具**（python-docx 能打开即证明 OOXML 合法） |
| Node 能否加载工作台自带 JSZip | 可加载，版本 3.10.1 | **用作生成工具**，与工作台同源 |

### （二）生成方式：自建最小完整 DOCX

不采用“复制现有模板再改正文”的方式，改为**自建最小完整 OOXML 包**，理由如下。

1. 现有模板（所函、材料清单）带有律所信头页眉、页脚、图片与三套页眉页脚引用，其版式服务于**律所致函**场景；程序性文书是**呈交法院**的申请人文书，格式不同，套用信头反而错误。
2. 现有模板含 `word/media/`、`word/theme/`、三组 header 与 footer、`docProps/custom.xml` 等十余个部件，任何一处引用关系出错都会导致文档损坏；自建包只需 5 个部件，出错面小。
3. 自建包的结构完全可控，段落样式可直接按律所公文标准写入 `styles.xml`，不依赖继承链。

生成的包结构如下：

```
[Content_Types].xml                    必需，声明各部件类型
_rels/.rels                            必需，指向 word/document.xml
word/document.xml                      正文
word/styles.xml                        样式定义（仿宋正文、黑体标题、页边距）
word/_rels/document.xml.rels           空关系（无页眉页脚与图片，故无外部引用）
```

### （三）版式参数

| 项 | 取值 | 对应 OOXML 元素与属性值 |
|---|---|---|
| 纸张 | A4，页面尺寸 11906 × 16838（缇） | pgSz |
| 页边距 | 上下 1440 缇（2.54cm），左右 1800 缇（3.18cm） | pgMar |
| 标题 | 黑体，22pt（字号值 44），加粗，居中 | rFonts、sz、b、jc |
| 正文 | 仿宋，12pt（字号值 24） | rFonts、sz |
| 行距 | 1.5 倍（行距值 360，规则 auto） | spacing |
| 首行缩进 | 2 字符（缩进值 200） | ind |
| 落款 | 右对齐，无首行缩进 | jc |

**说明**：现有委托材料模板的正文为楷体 15pt，本方案采用公文标准的仿宋 12pt。两者差异为**有意选择**，因程序性文书属呈交法院的诉讼文书，与委托合同类商业文书的排版惯例不同。此点列于第九部分待确认。

### （三）待填标记

工作台没有的要素（案号、请求数额、财产线索、待证事实、请求事项内容）统一以下列形式留空：

| 要素 | 写法 |
|---|---|
| 案号 | `（{{YEAR}}）粤________民初________号` |
| 金额 | `人民币________元` |
| 财产线索 | 编号列表，每行 `1. ________` |
| 请求事项 | 编号列表，每行 `一、________` |
| 日期 | `20____年____月____日` |

**为何用下划线字符而不用 Word 下划线格式**：工作台的注入规则中存在“查找带下划线格式的空白并替换”的规则（`blank_prefix`、`underline_after_prefix`）。若模板使用下划线**格式**，导入工作台处理时可能被规则误判为待填空白而发生意外替换。改用下划线**字符**（`_`）可规避该风险。

### （四）禁止事项

1. 不得出现 19 个白名单以外的 `{{...}}` 标记。
2. 不得使用 `{{CAUSE}}` 表达完整案由。工作台对该占位符的取值会自动去掉尾部“纠纷”二字，故完整案由应写作“{{CAUSE}}纠纷”。
3. 不得用 `{{UPFRONT_FEE}}` 表达请求保全数额或标的额，该占位符专用于律师费。
4. 模板正文中不得出现孤立的 `{{` 或 `}}`。

## 六、风险清单与规避措施

本节为本方案的核心。每一风险均给出触发条件、后果、规避措施与验证方法。

### 风险 1：破坏工作台现有功能

- **触发条件**：误改 `app/`、`data/`、`resources/` 下文件，或误跑构建脚本的删除逻辑。
- **后果**：工作台功能回退，属最高等级风险。
- **规避措施**：本次不打开上述目录下任何文件的写操作；生成脚本的输出路径硬编码为 `procedural-templates/`，执行前校验输出路径位于该目录内，越界即中止；不调用 `tools/build.cjs` 与 `tools/build.go`。
- **验证方法**：实施完成后重跑第 3.4.1 验证脚本（内置自检 21 项、版本号六处、工作包往返），结果须与本次修复后的基线完全一致。

### 风险 2：生成的 DOCX 无法被 Word 打开

- **触发条件**：OOXML 部件缺失、命名空间错误、XML 不闭合、关系引用悬空。
- **后果**：模板不可用，且人工打开时才发现。
- **规避措施**：只生成 5 个必需部件，不引入页眉页脚与图片，从根本上消除引用悬空；XML 全部由程序拼接并做闭合校验。
- **验证方法**：用系统 Python 的 python-docx **实际打开**每份 DOCX 并读取段落文本；python-docx 对包的完整性校验严格于 Word，能打开即可确认结构合法。另用 lxml 解析每个部件并检查命名空间声明。

### 风险 3：占位符越界导致导入工作台被拒

- **触发条件**：模板写入白名单外的 `{{...}}`。
- **后果**：用户若按可选路径导入，会被 `validateTemplate` 以“未知占位符”拒绝。
- **规避措施**：生成脚本内置白名单常量，逐份扫描正文提取全部 `{{...}}`，出现白名单外标记即中止脚本并报错。
- **验证方法**：脚本自检加独立校验脚本双重扫描，输出每份模板的占位符清单备查。

### 风险 4：`{{CAUSE}}` 取值语义偏差

- **触发条件**：模板写“案由：{{CAUSE}}”，而工作台取值已去掉“纠纷”二字。
- **后果**：填充后显示“案由：买卖合同”，语义不完整。
- **规避措施**：统一写作“案由：{{CAUSE}}纠纷”；生成脚本对该用法做专项扫描，发现裸用 `{{CAUSE}}` 且后接非“纠纷”二字的位置即告警。
- **验证方法**：脚本输出全部 `{{CAUSE}}` 的出现位置供人工过目。

### 风险 5：下划线格式被工作台注入规则误替换

- **触发条件**：模板使用 Word 下划线格式的空白，而工作台规则中存在按下划线定位的替换逻辑。
- **后果**：待填空白被规则当作目标位置替换，产生无意义内容。
- **规避措施**：待填标记一律使用下划线字符，不使用下划线格式；生成脚本不生成 `<w:u>` 元素。
- **验证方法**：校验脚本扫描 document.xml，断言不含 `<w:u` 标签。

### 风险 6：批次生成时单份出错未被发现

- **触发条件**：25 份模板由同一脚本批量输出，个别文件因数据错误静默失败。
- **后果**：个别模板内容缺失或错版。
- **规避措施**：生成脚本按份写入，每份写入后立即读回并校验段落数与文本非空；任一份不通过即中止整个批次，不产出半成品。
- **验证方法**：脚本以“全通过才落盘”的方式执行；落盘后再由独立校验脚本复核。

### 风险 7：误判为已接入工作台

- **触发条件**：用户误以为新模板已由工作台自动调用。
- **后果**：使用时找不到生成入口，或误在模板库中重复导入。
- **规避措施**：`procedural-templates/README.md` 首段明确写明“本目录不被工作台自动读取，需按第二部分步骤手工套用或按第三部分步骤导入”；README 另列与工作台模板库的区分说明。
- **验证方法**：README 内容评审。

### 风险 8：新版式与既有模板风格不一

- **触发条件**：程序性文书用仿宋 12pt，而委托材料用楷体 15pt。
- **后果**：同一律所两类文书排版风格不同。
- **规避措施**：此为有意选择，理由已写入第三部分；若确认需统一，改为楷体 15pt 仅需修改脚本中的两个样式常量并重跑，成本极低。
- **验证方法**：列于第九部分待确认。

### 风险 9：模板内容与已核验条文不符

- **触发条件**：转录模板清单内容时误改条号或条文要旨。
- **后果**：文书法条引用错误。
- **规避措施**：内容直接取自模板清单（该清单条文经元典法规库逐条核验），不重新撰写；生成脚本内嵌条文文本常量，不逐份手打。
- **验证方法**：校验脚本对每份模板扫描“第…条”字样，与清单中的条文记录逐条比对。

### 风险 10：新增资产未纳入版本追溯

- **触发条件**：新目录未记入 CHANGELOG 与构建烙印。
- **后果**：交付物与记录不符，重演 3.4.0 的发布证据链问题。
- **规避措施**：在 CHANGELOG 追加记录；烙印是否纳入列于第九部分待确认，若纳入则一并重算。
- **验证方法**：实施后核对 CHANGELOG 与烙印状态。

## 八、实施步骤
